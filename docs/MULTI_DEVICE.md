# 多设备账户与同步：实施边界

## 目标和现状

每位用户有独立账户，可在 Windows、Mac 和手机使用同一身份，看到自己有权限的项目、会话与设置；多人可被邀请加入同一会话。当前「我的设备」只是在一台主机上配对设备并远程访问该主机，主机关机或不可达时不能访问；本机 account.json 不是云端登录账户。

当前源码尚无云账户、跨独立安装的数据同步、常驻中继或移动原生客户端。现有扫码和本地会议继续可用，不能把它们标成云同步已经完成。

## 数据与权限边界

- 云账户和每台登录设备分别有稳定标识；设备可单独退出和撤销，不以 IP 地址认定身份。
- 会话由服务端持久化，并保存成员与各自权限；每次读取、发言及邀请都检查账户和会话成员资格。不同账户不可读取彼此未授权的会话。
- 会话消息、项目名称、成员权限、用户明确选择的通用设置可同步。消息与修改操作应有稳定 ID、版本和幂等键，确保重试不重复发送，冲突要显式处理。
- 项目本机路径、实际文件、运行中的进程、Harness 登录信息、访问令牌、密钥和自定义驱动中的敏感配置默认留在原设备。另一设备选择自己的工作目录和 Harness；附件同步需要单独设计存储和权限。
- 迁移旧数据必须由用户明确触发，先预览范围、保留本地副本；不能把 data 目录整体上传，也不能静默替换现有会话。
- 云同步和远程执行是两件事：关闭电脑后，已同步的内容可读，但该电脑上的 Harness 不会继续运行。自动回复需要对应设备在线并主动连接。
- 云服务和客户端使用 HTTPS，令牌安全存储、设备撤销、账号恢复、限流和备份都要在公开使用前完成。不能把占位登录或未部署服务描述为可用的账户系统。

## 推荐实施顺序

1. 确定部署位置、登录方式、账户恢复和预算；接入可靠身份服务及持久数据库，避免自行发明生产认证协议。
2. 建立账户、设备、会话、成员和消息的服务端模型；实现授权检查、设备撤销、数据库迁移及隔离测试。
3. 在桌面端提供登录、退出、设备列表及同步状态；先实现消息与项目基本信息同步，测试多用户隔离、断网重试和冲突。
4. 加入手机网页，沿用同一账户和会话权限；连接在线 Harness，并清晰显示哪台执行设备在线。
5. 分别处理旧数据迁移、附件、设置和多人协作；完成备份恢复、监控和真实 Windows / Mac / iOS 跨网络测试，再发布。

部署服务需要明确 Azure 或 AWS 资源、可用域名、邮件发送服务及运行费用。GitHub Pages 只能托管官网静态页面，不能代替账户与数据库服务。
