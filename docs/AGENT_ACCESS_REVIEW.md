# Agent 接入检查（2026-11-12）

本次检查源码、产品说明及接入相关测试。没有修改业务实现，没有操作真实联系人、宿主 MCP 配置或密钥，也没有调用真实模型。

## 已确认的问题

1. **切换 MCP 会覆盖本机执行配置，失败无回滚。** `bridge/discovery.py:336` 的 `connect()` 对非内置直连联系人先保存 `driver=external`，然后调用 `access.credential()` 重置密钥，最后才写宿主插件。插件安装失败时前两步仍已生效。隔离 mock 已复现：原驱动为 ACP，安装返回失败，但已保存 external 并调用密钥重置。这样也破坏了文档承诺的待命离线回落 CLI/ACP。
2. **扫描会把验证失败的自建联系人显示为已连接。** `_inspect_entry()` 用 `ready OR spec.user` 判断直连状态；这里的 user 表示配置来自 agents.d，不是连接证据。隔离 mock 已复现 `state=failed, user=True` 得到 `connected=True`。自定义条目的扫描也有同类判断。
3. **MCP 配置存在被当成连接成功。** 扫描用插件存在和密钥存在判断 connected，没有要求收到客户端认证或待命心跳；`install.installed()` 对非 Claude 宿主仅搜索文件中是否存在服务名，无法证明地址、凭据及协议正确。
4. **本机接入仍有两套流程。** 扫描弹窗走 discovery/connect，向导走 agents/add、restore 和 contacts/check，程序列表分别来自目录表和注册表。相同操作的配置保存和验证路径不同。
5. **身份归并尚未统一。** 目录表按 cursor 品牌一行归并，但预置仍有 cursor 与 cursor_desktop 两个 ID；不能据此自动认定它们是同一实例。联系人、品牌、执行端需要有清楚的边界。
6. **执行位置会隐式切换，状态展示未一致反映。** drivers.call 优先选择在线 MCP 待命端，离线才按 driver 调用；Room.state 对非 external 联系人仍按 local/http 返回 transport。实际执行位置与状态可能不一致。切换时复用 session_id 的行为还需要专门验证上下文隔离。
7. **验证说明不准确。** 向导统称本机验证只运行 --version，但 ACP 实际执行 probe 握手与建会话。程序可启动、协议可用、模型能回复是不同层次。

## 可选整理范围

1. **仅修故障。** 修状态误报、切换覆盖、失败回滚，保留当前入口。改动较小，但两套配置流程继续存在。
2. **统一接入流程（推荐）。** 先修上述故障，再让扫描仅提供候选程序；全部接入和已有联系人配置进入同一流程。后端统一提供配置状态、验证证据、执行端在线状态与本轮执行位置。保留联系人 ID、会话、权限；不按品牌自动合并身份。CLI/ACP/MCP/HTTP 参数放到高级设置。
3. **重构为联系人加独立渠道模型。** 明确联系人、多个执行渠道及各渠道会话上下文，支持显式选择和回落。能力完整，但需要数据迁移和更多回归，范围最大。

检查后选择方案 2，并进一步确定每会话执行端独占、共享同一原生会话、应用内模型索引与配置界面。
