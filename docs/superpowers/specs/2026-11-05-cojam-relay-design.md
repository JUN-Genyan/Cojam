# 合拍 Cojam：扫码组网设计

日期：2026-11-05
状态：已确认，实施计划见 `docs/superpowers/plans/2026-11-05-cojam-relay-v1.md`

## 1. 背景

会议室跑在用户自己的电脑上，只监听 `127.0.0.1`。跨设备今天只有一条路：用户自己在电脑上跑 `tailscale serve`，再把地址手工填进接入向导。目标用户是普通消费者，不能要求他们装 VPN、配隧道、理解域名和端口。

要做的产品能力是：**任何人打开合拍，他的其他设备扫个码就能加入这间会议室，不安装、不配置。** 手机在 4G、在另一个城市、在公司内网都能连，只要手机能上网。

效果对标 ZCode 的 Remote Control：桌面端显示二维码，手机扫码后在浏览器里操作，指令回到桌面端执行。不依赖微信或公众号，那属于另一条可选的入口。

开发者自己的机器不参与任何人的连接。中继是产品后端，每个用户各自用自己的电脑当主机，房间之间互相隔离。

## 2. 目标

- 不同网络：通过产品中继扫码加入，手机能上网就能进，不装软件、不配网络
- 同一 WiFi：可以作为不需要服务器的兜底路径，但不是 v1 的交付内容
- 加入的设备默认是访客，能看什么、做什么由主机在现有「成员与权限」界面授予
- 中继不可用时，本机功能完全不受影响

## 3. 非目标（v1 明确不做）

- P2P 打洞 / STUN / TURN
- 账号体系、注册登录、计费
- 微信 / 飞书机器人入口（以后可作为同一房间的另一个前端，不影响本设计）
- 访客上传下载文件（现有访客页本来就只支持文本）
- 远程 MCP 客户端走中继（v1 只支持浏览器扫码加入）
- 公网暴露主机端口、自动改防火墙、自动组网

## 4. 术语

| 术语 | 含义 |
|---|---|
| 主机 host | 开着会议室的用户电脑 |
| 中继 relay | 产品方运营的公网服务，只转发字节 |
| 房间 room | 一次主机注册产生的隔离通道，有独立房间号 |
| 邀请码 | 放进二维码的凭据，等价于现有联系人接入密钥 |
| 主机令牌 | 主机与中继之间的凭据，访客永远看不到 |

## 5. 阶段一：中继扫码（公网，主路径）

**交互**

1. 主机打开合拍 → 自动向中继注册房间 → 界面显示二维码和可复制的邀请链接
2. 访客用手机扫码，或把链接粘贴到浏览器打开
3. 浏览器打开中继上的访客页，显示「正在连接」，随后「等待主机授权」
4. 主机勾选权限后，访客进入会议室

访客所在的网络与主机无关：手机用 4G、在另一个城市、在公司内网都可以，只要能上网。整条路径不要求访客安装任何软件，也不要求主机开放端口、配置路由器或 VPN。

**这是产品的主路径，不是可选项。**

## 6. 中继架构

```
主机 A（合拍）──注册/长轮询──▶ 中继（公网 https）◀──浏览器 B/C
                                      │
                                      └── 托管访客页静态资源
```

**组件**

| 组件 | 位置 | 职责 |
|---|---|---|
| 主机适配器 | 桌面端内 | 出站注册、拉取任务、在本地执行、回传结果 |
| 中继服务 | 产品后端 | 分配房间、转发请求、托管访客页、限流 |
| 访客页 | 中继托管 | 与现有 `static/join.html` 同源构建，接口路径不变 |

**数据流**

1. 主机启动 → `POST /v1/host/register`（安装 ID、显示名）→ 得到 `room_id` + `host_token`
2. 主机维持 `GET /v1/host/pull?room=`，长轮询 25 秒，取到一条待执行请求
3. 适配器在本机执行该请求（只允许白名单路径），`POST /v1/host/result` 回传
4. 访客打开 `https://<中继域名>/j/<room_id>#<邀请码>` → 中继返回访客页 → 页面的 API 请求打到中继 → 中继塞进该房间的请求队列 → 主机执行 → 结果回传 → 中继返回给访客
5. 主机断开超过 60 秒，房间作废，二维码和链接立即失效

**协议草案**

| 接口 | 方向 | 说明 |
|---|---|---|
| `POST /v1/host/register` | 主机 → 中继 | 返回 `room_id`、`host_token`、`expires_at` |
| `GET /v1/host/pull?room=` | 主机 → 中继 | 长轮询，返回一条请求或 204 |
| `POST /v1/host/result` | 主机 → 中继 | `job_id`、状态码、响应头、响应体 |
| `GET/POST /j/<room>/...` | 访客 → 中继 | 原样对应主机上的白名单路径 |

长轮询而不是 WebSocket：项目零依赖（`pyproject.toml` 的 `dependencies = []`），现有成员连接端已经是轮询 + 心跳的成熟模式，不引入新依赖。

## 7. 局域网直连（2026-11-05 已实现，作为中继之前的第一步）

同一 WiFi 内扫码直连，零安装、零服务器成本：

- 保持 `127.0.0.1:8765` 管理监听不变，另起一个只绑私有 IPv4 的 `ExclusiveServer`（默认 `8766`），复用同一个 Handler
- 私网地址识别在 `bridge/common.py`：优先默认路由，跳过回环、链路本地、公网和 `100.64.0.0/10`（Tailscale / 运营商 NAT）
- 访客页识别沿用现有逻辑：Host 不是 localhost、有转发头、来源不是回环，就返回 `join.html`
- `/api/server/info` 返回 `lan_url`；邀请向导默认用它，并显示本地生成的二维码（`static/qrcode.min.js`，不经过外部服务）
- 局域网入口照样过 `_from_browser()` 和联系人密钥：管理接口、`/api/server/stop` 在局域网地址上返回 403
- Windows 首次监听会弹防火墙提示，需要允许“专用网络”
- 限制：HTTP 明文，适合可信 WiFi；公共 WiFi 可能开了 AP 隔离；DHCP 换地址后旧邀请会失效，重新生成即可

中继 v1 仍是跨网络、对方零安装的兜底路径；局域网这条不依赖中继，也不产生流量成本。

## 8. 路径白名单（代码强制）

访客页实际只用四条接口。访客页本身和它的静态资源（`guest.css`、`logo.svg`、`icon-192.png`）由中继直接从仓库构建后托管，不经过主机，所以转发白名单只有这四条，多一条都不放：

| 方法 | 路径 |
|---|---|
| GET | `/api/external/rooms` |
| GET | `/api/external/messages` |
| POST | `/api/external/hello` |
| POST | `/api/post` |

`/mcp`、`/api/rooms`、`/api/agents`、`/files/`、`/api/server/*`、`/static/*` 以及一切管理员接口**不在转发白名单内**。局域网模式没有中继，访客页和静态资源仍由主机自己提供。

强制点有两处，缺一不可：

- 中继侧：房间上只接受上述路径，其余直接 404，不进队列
- 主机侧：适配器再校验一次，命中白名单才在本地发起请求

主机侧是最后一道防线：中继被攻破或被改成恶意实现时，主机仍然不会被穿透。

## 9. 安全设计

- **管理员能力不可达**：适配器从不注入 `X-RT-Token`，并且从传入请求里剥掉 `X-RT-Token`、`Cookie`、`X-Forwarded-*`。主机上的 `_from_browser()`（`bridge/web.py:66-69`）因此永远返回假，管理员接口对访客关闭
- **邀请码不经过中继存储**：和现有做法一致，放在 URL fragment，只由浏览器和主机两端持有；中继日志不记录 `Authorization`、不记录请求体和响应体
- **主机令牌只属于主机**：访客页面拿不到，房间号猜不到（随机 128 位）
- **默认最小权限**：扫码进来的设备默认只有「读取会话」，发言和其他能力由主机勾选；与现有邀请默认值（读取/发言/唤起）不同，扫码场景面向不确定设备，收紧一档
- **防滥用**：房间限时、限设备数（默认 5）、单房间限速、单 IP 限速；中继不接受匿名注册以外的主机请求
- **离线优先**：中继不可达时，主机适配器进入退避重试，本机会议、本机 AI 全部照常
- **不自作主张**：不修改防火墙、不开公网端口、不自动申请证书

## 10. 权限与授权

沿用现有权限模型：读取会话 / 发言 / 唤起其他 AI / 编辑看板 / 分享本机文件 / 允许干活。

- 访客扫码后先进入「等待授权」，主机页面弹出请求（复用现有联系人接入的事件流）
- 授权界面就是现在的「成员与权限」，不新增一套
- 授权前访客只能看到"已申请"，看不到会议内容；未授权状态不落盘成成员

## 11. 部署与成本

- 起步一台 1C1G 的 VPS 足够；带宽主要是长轮询空转和文本消息，量很小
- 面向国内用户需要境内服务器 + 已备案域名；域名和证书由中继统一负责，用户完全无感
- 观察指标：在线房间数、每房间请求速率、中继出站带宽、被限流的 IP 数

## 12. 测试点

- 白名单：管理接口、`/mcp`、`/files/` 经中继访问必须 404，且主机侧有独立拒绝记录
- 凭据：`X-RT-Token`、`Cookie` 被剥离后 `_from_browser()` 为假
- 生命周期：房间过期、主机掉线、中继不可达、主机重连
- 权限：默认只有读取；授权后逐项生效；撤销立即失效
- 隔离：两个房间并发，消息不串
- 回归：现有 `tests/run_all.py` 全绿；不引入新依赖

## 13. 分阶段交付

1. **阶段一**：中继服务 + 主机适配器 + 访客页托管 + 二维码，做到"手机任意网络扫码即入"
2. **阶段二**：局域网直连兜底（无服务器、断网可用）
3. **后续**：微信 / 飞书入口、远程 MCP 走中继、打洞优化、账号与额度

## 14. 开放问题
